# Tests

## Test A - Double submit creates only one order
Viewport: mobile (375x667)
Covers: POST /api/orders idempotency, frontend submit lock, duplicate-click guard
Description: Verifies rapid repeated taps cannot create duplicate orders.

Steps:
1. Add one product to cart and continue to Thanh toán
2. Tap Tiền mặt twice rapidly
3. Open Theo dõi đơn or Admin Đơn hàng and review the newest order

Expected: The payment buttons disable immediately with Đang xử lý..., exactly one order is created, and a retry with the same checkout request returns the same order instead of creating another.

## Test B - Quick topping, cart persistence and total recalculation
Viewport: mobile (375x667)
Covers: customer product-card + Topping control, compact topping picker, localStorage cart persistence, size switching, topping selection, total recalculation
Description: Verifies a customer can add pudding/topping directly from the menu card without a long option form, while the selected charge remains correct.

Steps:
1. On one product card choose Size M + Pudding trứng and add one cup; add the same Size M again with Trân châu đen instead
2. Add another cup with the exact same Size M + Pudding trứng configuration, then open the cart and change topping on one cup from any multi-quantity line
3. Refresh the page, reopen the cart and Thanh toán

Expected: Same product and same size with different topping combinations appear as separate cart lines; only identical product + size + topping configurations merge quantity. Editing topping on a line with quantity greater than one splits exactly one cup into its own configuration. Each line itemizes its own topping charge and all totals remain correct after refresh.

## Test C - Out of stock blocks order and payment
Viewport: desktop (1280x800)
Covers: prepared-base stock guard, topping inventory guard, POST /api/orders 409, POST /api/orders/:id/payment stock recheck
Description: Verifies inventory cannot go negative and an unavailable ingredient/base prevents a sale.

Steps:
1. As Admin, manage a base recipe by cooking a batch, then reduce/consume it until below the amount required for a product; alternatively reduce a topping ingredient below one serving
2. Attempt to create an order that requires that unavailable base or topping
3. If an older pending order exists, attempt to confirm payment after its required stock becomes unavailable

Expected: The app refuses the action with a clear Tạm hết message, no new invalid order/payment transition is created, and stock never becomes negative.

## Test D - Network or API failure is visible and retry is safe
Viewport: mobile (375x667)
Covers: checkout error handling, network/API failure message, idempotent retry
Description: Verifies uncertain checkout failures do not silently duplicate an order.

QA Faults:
```json
[{"method":"POST","path":"/api/orders","status":500,"body_json":{"error":"Lỗi thử nghiệm khi tạo đơn"}}]
```

Steps:
1. Add a product and submit checkout while the simulated API failure is active
2. Verify the checkout remains available and shows the returned error clearly
3. Remove the fault and submit again

Expected: The cart is not cleared on failure, a visible error is shown, the button unlocks for retry, and a successful retry creates at most one order.

## Test 2 - Admin dashboard aggregates by selected period
Viewport: desktop (1280x800)
Covers: BL avatar workspace navigation, sticky topbar, removal of redundant bottom role bar, Admin dashboard period filter, interactive week/month/year revenue comparison chart, monthly/yearly/custom aggregation, VAT-inclusive gross revenue, pre-VAT revenue, embedded VAT payable, revenue/order KPIs, staff POS revenue by actor, barista revenue reconciliation, mobile Admin Dashboard responsive overflow/stacking
Description: Verifies Admin can summarize business results by useful reporting periods instead of mixing all historical orders together.

Steps:
1. Sign in as Admin, tap/click the BL avatar and verify the dropdown contains Dashboard Admin, POS Thu ngân, Pha chế and Xem như khách while no fixed bottom role bar is shown; choose Dashboard Admin and open Tổng quan
2. Switch Báo cáo doanh thu between Hôm nay, Tháng này, Năm nay and Tùy chọn ngày; then in So sánh doanh thu switch Tuần, Tháng and Năm. In Tuần verify Thứ 2 through Thứ 7 all fit inside the chart on mobile without horizontal scrolling, then click individual column groups
3. Review Doanh thu đơn, Tổng thu and Số đơn after each change; then review Theo dõi doanh thu từng nhân viên and verify each account has separate Lên đơn/DT lên đơn and Nhận pha/DT nhận pha values. Verify Lên đơn counts only paid POS orders created by that account, while Nhận pha is credited when a barista accepts a paid order with Nhận đơn / Bắt đầu pha, including customer web orders. Change the store to Tạm đóng cửa and return to Dashboard to verify the report remains accessible

Expected: The topbar remains fixed while scrolling; role/workspace shortcuts are grouped inside the BL avatar dropdown and the old fixed bottom role navigation is absent. On mobile, Admin Dashboard does not push the whole page wider than the viewport: KPI cards stack cleanly, filters/buttons wrap, CRUD tables scroll only inside their own containers, forms use one column, and the weekly comparison chart fits Thứ 2 through Thứ 7 in one compact responsive row without horizontal scrolling; longer Month/Year views remain contained inside their chart frame. KPI values recalculate from orders inside the selected period; Admin sees revenue including VAT, revenue before VAT, and embedded VAT where VAT = gross × 10/110. The comparison chart uses paid order data, shows two bars for current versus previous period, changes grouping for Tuần/Tháng/Năm, and clicking a column group shows the selected amounts and difference. Individual employee revenue credits only two actions: paid POS orders to the account that created the customer order, and preparation revenue to the barista account stored in claimedBy when that barista accepts the order with Nhận đơn / Bắt đầu pha. Customer web orders do not credit order-taking revenue but can credit preparation revenue. Payment confirmation, preparation completion, and delivery actions do not add employee revenue. Closing or temporarily closing the shop affects customer ordering status only and does not block Admin from opening or checking revenue reports.
